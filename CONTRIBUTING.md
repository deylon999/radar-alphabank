# Как вносить изменения

## Ветки

- `main` — то, что развёрнуто на Vercel. Прямо в `main` не пушим: только через pull request.
- Работа идёт в короткоживущих ветках от свежего `main`:
  `feat/…` — новое, `fix/…` — исправление, `refactor/…`, `docs/…`, `chore/…` — остальное.
  Пример: `feat/client-search`, `fix/theme-flicker`.
- Ветка живёт день-два. Долгую задачу режем на несколько PR.

## Pull request

- Заголовок — в формате [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/),
  его проверяет CI (`pr-title`):

  ```
  <тип>(<область>): <что сделано>
  ```

  Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `style`, `build`, `ci`, `chore`,
  `revert`. Область — необязательная: `frontend`, `backend`, `bot`, `api`.
  Примеры: `feat(frontend): обзор по темам`, `fix(api): 404 для неизвестного клиента`.
  Ломающее изменение договора API — с `!`: `feat(api)!: topic обязателен у инсайта`.

- Описание — по шаблону: что сделано, как проверить, чек-лист.
- Перед слиянием CI должен быть зелёным: `frontend / check` (типы, линтер, unit-тесты,
  сборка), `frontend / e2e`, `bot / bot` (`go vet`, `gofmt`, `go test`) и `api / spec`
  (спецификация собирается без предупреждений). Проверки бота и спецификации запускаются,
  только если в PR менялись `bot/` или `api/`, иначе засчитываются пропущенными.
- Слияние — только **Squash and merge**: в `main` одна запись на PR, её текст — заголовок PR.
  Ветка удаляется автоматически.

## Коммиты внутри ветки

- Маленькие и осмысленные: один коммит — одно изменение, которое можно описать одной фразой.
- Сообщение — в повелительном наклонении, до 72 символов, без точки в конце:
  `Add client search`, `Fix theme flicker on toggle`.
- Не коммитим: `.env` и токены, данные кейса (CSV, PDF банка), сборку (`dist/`), отчёты тестов.

## Перед пушем

```bash
cd frontend
npm run check   # типы, линтер, unit-тесты, сборка
npm run e2e     # если менялись экраны
```
